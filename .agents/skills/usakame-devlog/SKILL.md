# Usakame Devlog（開発日誌）作成ワークフロー

このスキルは、AIが書いた長くて退屈な変更ログ（Changelogの羅列）になるのを防ぎ、**開発者の「設計意図・課題意識・取捨選択」を最小の手間（数行の返答）で引き出し、3分で読める開発日誌（約1,200〜1,600文字）**を `docs/blog/` に作成するためのワークフローです。

いきなり記事の本文を書き始めてはいけません。必ず以下の **Step 1 → Step 2 → Step 3** の対話ステップを踏んでください。

---

## Step 1: 対象期間の確認とトピック候補（最大3つ）の抽出・質問

1. **対象期間の特定**:
   * ユーザーから期間指定がない場合は、`docs/blog/` 内の最新記事の対象期間を確認し、その翌日から現在（または2週間分）を対象期間とします。
2. **コミット履歴の取得**:
   * `git log --since="YYYY-MM-DD" --until="YYYY-MM-DD" --reverse --format="%h %ad %s" --date=short` を実行して期間内のコミット一覧を取得します。
   * 必要に応じて `devlog_notes.md` などのメモファイルがあれば読み込みます。
3. **トピック候補（最大3つ）への絞り込みと質問の提示**:
   * 細かいバグ修正や単なる内部リファクタリングは無視し、**ブログ読者（レトロゲーム開発者、Rust / mruby / AIエージェント活用に興味がある人）が興味を持ちそうなトピックを最大3つ**に絞ります。
   * 各トピックについて、以下のフォーマットでユーザーに提示し、**一旦ターンを終了してユーザーの回答を待ちます**。
     * **タイトル案**
     * **期間・主なコミット**
     * **内容の要約（2〜3行）**
     * **💬 開発者への質問（1つ）**: コミットログからは読み取れない「なぜこの設計にしたのか」「どこに苦労・工夫したか」「作ってみてどうだったか」を引き出す質問を1つ添えます。

---

## Step 2: スクリーンショット・GIF画像のピックアップ

ユーザーから採用トピックとコメントが返ってきたら（または画像ピックアップを求められたら）、対象期間内に撮影・作成された画像を探します。

1. **検索対象ディレクトリ**:
   * リポジトリ内: `screenshots/`, `examples/`, `docs/`
   * 隣接リポジトリ（存在する場合）: `..\usakame-games\images`, `..\usakame-gallery\images`
     （※ サンドボックス制限で隣接フォルダにアクセスできない場合は `BypassSandbox: true` で検索・コピーを行います）
2. **画像の選定と配置**:
   * ファイルの更新日時（`LastWriteTime` / `CreationTime`）やファイル名から、対象期間・採用トピックに合致する `.png` / `.gif` をリストアップします。
   * `read_file` ツールで実際の画像の中身を視覚的に確認し、記事の各セクションに最も合う画像を選びます。
   * 隣接リポジトリ（`..\usakame-games\images` や `..\usakame-gallery\images`）の画像を使用する場合は、リンク切れを防ぐため `screenshots/`（または `docs/blog/images/`）にコピーした上で相対パスでリンクするか、ユーザー指定のパス形式でリンクします。
   * もし動く `.gif` が欲しいトピックで画像がない場合は、`cargo run --bin uk -- run <script.rb> --gif screenshots/<name>.gif --frames 180` での撮影を提案・実行しても構いません。

---

## Step 3: 記事の執筆と `docs/blog/` への保存

ユーザーのコメント（設計意図・背景）とGitの正確な事実、ピックアップした画像を組み合わせて、`docs/blog/YYYY-MM-DD-devlog-<N>.md` に記事を作成します。

### ✍️ 文章規範（`japanese-tech-writing` スキルの必須適用）

**記事を執筆・推敲する際は、必ず同リポジトリ内の [`.agents/skills/japanese-tech-writing/SKILL.md`](../japanese-tech-writing/SKILL.md) を読み込み、その規範を適用してください。**

特に以下のルールを徹底します。

1. **『[`japanese-tech-writing`](../japanese-tech-writing/SKILL.md)』の適用**:
   * **段落と論証の構成（パラグラフライティング）**: 1段落1トピックとし、段落の先頭文を読めば何の話か分かるようにする。論証は一方向に進め、結論を出した後に理由を補足して再び結論を言い直す構成にしない。
   * **論証の厳密さ**: 「AだからBになる」の結果だけでなく、その因果の機構（なぜそうなるのか）を一文で明示する。「必ず解決できる」「完全にゼロになる」といった誇張を避け、条件や不確実性を正確に書く。
   * **演出の抑制とLLM口調の排除**: 本文中の太字強調（`**...**`）や感嘆符（`！`）の乱用、空虚な強調語（「非常に」「劇的に」「圧倒的に」「正面から扱う」「深掘りする」）、翻訳調の比喩・擬人化（「〜が効く」「データを運ぶ」など）を使わない。
   * **見出しの付け方**: 見出しは節の結論を言い切るセリフにせず、その節が扱う対象や答える問いを指す具体的な句にする。
2. **「全部書かない」ルールと分量制限**:
   * 期間中のコミットを網羅せず、ユーザーが選んだ **2〜3個のメインテーマ** だけを掘り下げる。
   * 選ばれなかった他の機能追加は、記事末尾の `## 今期のその他の実装` セクションに **箇条書き3〜4行以内** で簡潔にまとめる。
   * **記事全体で 1,200〜1,600文字程度**（読了3分）、**1トピックあたり 400〜600文字程度** に収める。
3. **整形とビジュアルレイアウト**:
   * 一文一改行を基本とし、和欧文・半角数字の境界には半角スペースを入れる。
   * 各メイントピックに1箇所以上、画像（`![キャプション](../../screenshots/xxx.png)`）を挿入する。
   * 複数のサンプルゲーム画面やエディタ画面を並べる際は、縦に間延びしないよう **Markdownテーブル（2〜3列）で横並び** に配置する。
