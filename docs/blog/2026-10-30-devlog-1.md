# 【開発日誌 #1】Rust と mrubyedge で作るレトロゲームエンジン「Usakame」の設計と、擬似ボタン連打による自動検証

**対象期間**: 2026年10月17日 〜 10月30日

Rust（Macroquad）と軽量 Ruby VM「mrubyedge」を組み合わせたレトロゲームエンジン「[Usakame（うさかめ）](https://github.com/ongaeshi/usakame)」を開発しています（シングルバイナリで動作します）。
この記事では、開発開始から最初の 2 週間で実装した「1 ファイル完結型のスクリプト構造」と、AI エージェントが生成したコードの実行時エラーを検出する「ガチャキーモード（`uk check -g`）」の設計意図をまとめます。

## 1. リソースまで 1 つの Ruby ファイルで完結させる理由

Usakame は、Ruby で手軽にゲームを書ける環境を目指して開発を始めました。
ゲーム制作を始めるとき、グラフィックやサウンド用の外部ツールを別途用意してファイルの読み書きを管理する手順は、開発の立ち上がりを遅くします。
昔のパソコンの BASIC のように、プログラムもデータもすべて目の前のコードだけで表現できれば、初心者もコードを生成する AI エージェントも、1 つのファイルの編集だけに集中できます。

そこで Usakame では、ゲームのロジックだけでなく、スプライト（ドット絵）・タイルマップ・効果音（SFX）・BGM まで、すべて 1 つの `.rb` ファイル内にプレーンテキストで記述できる構造を採りました。
Ruby スクリプト末尾の `__END__` 以降に、`@SPRITE` や `@MAP` といったセクションを置いてリソースを定義します。
手描きのドット絵だけでなく、内蔵した Twemoji による絵文字スプライトや、美咲フォント（8×8）・東雲フォント（16×16）による日本語テキストも外部ファイルなしで描画できます。

```ruby
def update
  # ゲームロジック
end

def draw
  cls(0)
  spr(:hero, 120, 120)
  print_text("うさかめエンジン！", 80, 100, 7)
end

__END__
@SPRITE :hero
..7777..
.744447.
...
```

![PC-98風640x480解像度と東雲ゴシック・絵文字描画デモ](../../screenshots/2026-10-19_pc98_resolution.png)

この 1 ファイルスクリプトを入力として、`uk run`（ホットリロード実行）、`uk build`（単一実行バイナリ出力）、`uk browser`（WebAssembly でのブラウザ実行）の 3 つの実行形態を開発初日に実装しました。

## 2. mrubyedge の未実装メソッド問題と、擬似ボタン連打検証（`uk check -g`）

1 ファイル完結の構造にしたことで AI エージェントによるゲームの自動生成が容易になった反面、生成されたコードが `mrubyedge` の未実装メソッドを呼び出して実行時にクラッシュする問題が頻発しました。
Usakame が採用している `mrubyedge` は WebAssembly 環境でも軽量に動作する一方、標準の CRuby や mruby にある組み込みメソッド（`Array#sample` や `Integer#upto` など）の一部を実装していません。
AI エージェントは標準 Ruby の知識を前提にコードを生成するため、これらの未実装メソッドを呼び出して `NoMethodError` を引き起こします。

まず 1 つ目の対策として、`mrubyedge` で利用可能なメソッド一覧と、未実装メソッドの代替イディオム（たとえば `array.sample` の代わりに `array[rand(array.size)]` を使うなど）を明記した [`docs/mrubyedge_api.md`](../mrubyedge_api.md) を整備しました。
コンパイル済みの `.mrb` バイトコード検証とドキュメント参照のどちらが有効かを AI エージェント自身にも比較させたところ、明確な代替パターン表をプロンプトの文脈に含める方が未実装メソッドの呼び出しを防ぎやすいという結果になり、実際に生成時のエラーは減少しました。

しかし、ドキュメントの整備だけでは防ぎきれない実行時エラーが残りました。
ゲームプログラムでは、起動直後のタイトル画面や待機状態では問題が起きず、プレイヤーがボタンを押して移動や攻撃の座標計算・当たり判定が始まった瞬間にだけ未定義メソッドや型エラーを踏むケースが多いためです。

そこで 2 つ目の対策として、GUI ウィンドウを開かずに指定フレーム数だけ高速実行するヘッドレス検証コマンド `uk check` に、方向キーやパッドのボタンを擬似的に連打しながら実行する `-g`（ガチャキー）オプションを追加しました。

```powershell
# ウィンドウを開かず、方向キーとボタンを擬似連打しながら 120 フレーム分の実行時エラーを検証
uk check game.rb -g --frames 120
```

AI エージェントの作業ルール（`AGENTS.md`）に「コードを生成・修正したら必ず `uk check -g` を実行して検証すること」を組み込んだ結果、生成されたコードが起動直後や操作開始直後にクラッシュする事象をほぼ事前に検出・自己修復できるようになりました。

## 今期のその他の実装

* エンジン内蔵スプライトエディタ: Usakame 自身の Ruby スクリプトで動作するスプライトエディタ（`uk edit`）を実装し、単一 `.rb` ファイル内の `@SPRITE` セクションへの非破壊保存に対応しました。
* 実行時エラーのオーバーレイ表示: スクリプトエラー発生時にウィンドウを終了させず、画面上に赤枠でスタックトレースを表示し、ファイルを保存すると自動で再読み込みして復帰する仕組みを導入しました。
* カスタムパレットと UI サンプル: `@PALETTE` セクションによるパレット定義・切り替え機能や、RPG 会話ウィンドウ・コマンド戦闘 UI などのサンプルを追加しました。

## 3. インストールと基本的な使い方

Usakame のソースコードとビルド済みバイナリは GitHub リポジトリ（https://github.com/ongaeshi/usakame ）で公開しています。

Usakame は、Ruby コンパイラ・実行 VM・フォント・絵文字アセット・内蔵エディタ・サンプル集までを 1 つの実行ファイル（`uk` / `uk.exe`）に収めたシングルバイナリとして動作します。
そのため、PC に Ruby や Rust の開発環境をインストールしなくても、GitHub Releases（https://github.com/ongaeshi/usakame/releases/tag/latest ）からアーカイブをダウンロードして展開するだけで利用できます（GitHub Actions で Windows / macOS / Linux 向けのバイナリをビルドしていますが、現在開発者が実機で動作確認しているのは Windows のみです）。

展開した `uk` コマンドを PATH の通ったディレクトリに置くと、以下のコマンドで新規プロジェクトの作成からホットリロード実行、内蔵スプライトエディタでの編集、配布用バイナリの出力までを行えます。

```powershell
# 1. 新規プロジェクトを作成して実行（ファイル保存で自動ホットリロード）
uk new myapp
cd myapp
uk run

# 2. ジャンル別テンプレートから作成（shooter, puzzle, card, platformer, dungeon など）
uk new my_stg -t shooter
uk run my_stg/game.rb

# 3. 内蔵スプライトエディタを起動して game.rb 内のスプライトを編集
uk edit game.rb

# 4. 内蔵サンプル集をカレントフォルダに展開して試す
uk examples ./examples
uk run examples/card_roguelite.rb

# 5. ブラウザ（WebAssembly）で実行、または配布用の単一実行バイナリを出力
uk browser game.rb
uk build game.rb -o my_game.exe
```
